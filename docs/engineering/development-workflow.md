# 개발 workflow

이 문서는 특정 작업의 목록이나 상태가 아니라, 어떤 개발 작업이든 완결되었다고 판정하기 위한 일반 원칙을 소유한다. 제품별 기준은 이 문서에 복제하지 않는다.

## 1. 정본과 추적성

판단은 다음 순서를 따른다.

1. `docs/plan/00~07`
2. 해당 정의를 소유하는 `docs/design/00~16`
3. 이 디렉터리와 [CONTRIBUTING.md](../../CONTRIBUTING.md)의 일반 개발 규칙

하위 문서가 상위 정본과 다르면 상위 정본을 따른다. 정본 근거가 없는 제품 구현을 시작하지 않는다. 새 제품 결정이 필요하면 구현으로 추측해 채우지 않고 소유 정본에서 먼저 해결한다.

## 2. 착수 전 완료 조건

작업을 시작하기 전에 다음을 명확히 한다.

- 하나의 일관된 변경 목적과 명시적인 제외 범위
- 판단 근거가 되는 계획·소유 설계 문서
- 명령, 테스트 또는 관측값으로 판정할 수 있는 완료 조건
- 동작 변경을 검증할 테스트와 적용할 품질 gate

시간 단위 크기, stage ID, 단위와 commit의 일대일 대응은 일반 완료 조건이 아니다.

## 3. 구현 완료의 정의

개발 작업은 다음 조건을 모두 만족해야 `implementation complete`로 볼 수 있다.

1. 코드와 그 동작을 검증하는 테스트를 같은 작업 범위에서 완료한다. 테스트를 후속 작업으로 미루지 않는다.
2. 완료 조건은 파일 생성 여부나 주관적 선언이 아니라 기계적으로 판정 가능하다.
3. 변경과 관련된 로컬 품질 gate와 CI를 통과한다.
4. 공개 계약, 운영 절차 또는 정본 문맥이 바뀌면 해당 소유 문서도 함께 일치시킨다.
5. 리뷰에서 확인된 결함을 해결하고, 결함을 재현할 수 있으면 회귀 테스트를 추가한다.
6. 실제 검증 명령과 결과를 남긴다. 실패하거나 검증되지 않은 작업을 완료로 표시하지 않는다.

구체적인 테스트 계층, 제품 품질 기준과 CI job은 [테스트·품질 설계](../design/16-testing-and-quality.md)가 소유한다. 실행 시간이 길다는 이유로 정본 gate를 약화하거나 이 문서에 다른 기준을 만들지 않는다.

## 4. 리뷰와 결함 처리

- 리뷰는 변경을 해당 정의의 소유 정본과 대조한다.
- 안전·금융 정확성 불변식, 정본 충돌 또는 테스트 공백이 발견되면 완료 판정을 취소하고 수정 후 다시 검증한다.
- 변경 범위와 무관한 결함은 숨기거나 현재 commit에 섞지 않고 별도 작업으로 분리한다.
- 해결하지 못한 검증 실패는 원인과 영향이 드러나는 blocker로 남긴다.

## 5. 구현 완료와 운영 gate

`implementation complete`는 코드·테스트·문서와 관련 품질 gate가 완료되었다는 뜻이다. 시간 경과, 무사고 운용, 실계좌 검증 또는 외부 확인이 필요한 `operational gate complete`와는 다른 상태다.

운영 gate와 마일스톤 순서의 정본은 [개발 로드맵](../plan/04-roadmap.md)이다. 코드가 green이라는 이유만으로 마일스톤을 진전시키지 않으며, 운용 증거가 실패했거나 아직 수집되지 않았으면 운영 완료로 표시하지 않는다. 반대로 운용 대기 자체를 구현 작업으로 간주하지 않는다.

## 6. 조건부 기능과 외부 확인

외부 사실이 필요한 값은 임의로 확정하지 않는다. 정본의 `[확인 필요]` 표기와 확인 방법을 따르고, 정본이 지정한 fallback이 있을 때만 그 경로를 사용한다.

조건부 기능은 gate 결과 없이 무조건 구현하거나 무조건 폐기하지 않는다. 기존 양쪽 경로와 조건을 보존하고, 새로운 제품 판단이 필요하면 구현을 중단해 소유 정본에서 해결한다.

## 7. 진행 상태 비소유

이 문서는 backlog, 작업 ID, 담당자, 구현 순서, 완료 수, 진행률, 상태 기호 또는 현재 작업 위치를 기록하지 않는다. 실패한 작업을 완료로 바꾸는 상태 갱신 규칙도 두지 않는다.
