# 00. 설계 총괄 — 문서 맵 · 공통 규약 · 추적성

> 이 문서 세트(`docs/design/00~16`)는 **구현 착수를 위한 설계 정본**이다. 상위 정본은 계획 문서 세트(`docs/plan/00~07`)이며, 설계와 계획이 충돌하면 **언제나 계획이 이긴다**. 설계서는 계획의 판정을 구현 수준으로 구체화할 뿐 계획의 결정을 뒤집지 않는다.
>
> 목표는 MVP가 아니라 **'초고성능 자동 자산 투자 운용 관리 로보 어드바이저 애플리케이션'의 최종 목표 시스템 전체**다. 계획이 조건부로 둔 요소(M9 `T1` 실시간 계층, SP-C4 절세계좌 주문 경로 등)는 **조건부임을 명시한 채 양쪽 경로를 모두 설계**했다.

### 1.1 소유권 경계 — 중복 정의 금지

같은 인터페이스·스키마를 두 문서가 각각 정의하면 반드시 어긋난다. **소유 문서만 정의하고 나머지는 참조한다.** 비소유 문서가 인용할 때는 `(정의 정본: 05-broker-gateway.md §7)` 형식으로 출처를 명시한다.

경계 사례 확정:

- **DDL은 03이 소유**, 그 테이블을 쓰는 **절차·로직은 각 기능 문서**(08·09·11)가 소유한다.
- **pre-trade 체인의 순서·단계 정의는 09가 소유**, 08은 집행 흐름 안의 호출 지점만 설계한다.
- **WS 세션·파싱은 05가 소유**, 이벤트 소비(가드·감시)는 11이 소유한다.
- **순매수 회계는 09가 소유**, 08은 `order_lock` 안에서의 호출 계약만 갖는다.
- **출처 태그(`OrderIntent`)는 02가 단독 소유** — §4.2 참조.

## 3. 공통 규약

### 3.1 환각 금지 체계 (이 세트의 최우선 규율)

계획 문서에 근거가 없는 단정은 이 문서 세트에서 **결함**으로 취급한다. 모든 수치·임계값·enum·상태명·테이블/컬럼명·TR ID·API 필드·법령/세제 값은 아래 셋 중 하나의 형태를 가져야 한다.

| 형태 | 표기 | 의미 |
|---|---|---|
| **계획 근거** | `(정본: 02 §4.3)`, `[→ 03 §1.2]` | 계획 문서에서 가져온 값. 출처 절이 명시된다 |
| **설계 결정** | `> **[DD-<문서>-<번호>] 제목**` 블록 (결정·근거·계획과의 관계 3항) | 계획이 비워 둔 여백을 설계가 채운 것. **선언된 창작은 정상 산출물이다** |
| **미확인 사실** | `[확인 필요] — <확인 방법>` | 계획에 없고 설계가 단정해서도 안 되는 외부 사실. 확인 수단(스파이크 ID·공식 문서·실측)을 함께 적는다 |

이 셋 중 어느 것도 아닌 단정이 **환각**이다. 계획 문서 참조는 `00`~`07` 번호를 쓰고, 설계서 상호 참조는 상대 링크를 쓴다.

### 3.2 정본 위계

문서 간 값이 충돌하면 아래 순서로 판정한다.

1. **계획 문서** — 집행 스펙 = 계획 02, 안전장치 파라미터 = 계획 03, 모듈 구조·인프라 = 계획 01, 실시간·감시 = 계획 06, 자가 개선 = 계획 07, 자동화 등급 = 계획 00 §3, 근거 = 계획 05. **import-linter 계약의 유일 원문은 계획 01 §2.2**.
2. **설계서 소유 문서** — §1 표의 "소유하는 정의" 열.
3. 그 외 문서의 인용은 사본이며, 사본이 정본과 다르면 **사본이 틀린 것**이다.

### 3.3 계획이 배제한 것은 설계로 되살리지 않는다

계획 00 §6(의도적으로 하지 않는 것)·계획 02 부록 B·계획 04 부록 A·계획 06 부록 B가 배제한 항목 — LLM 매매 판단, 자동 전량 청산, 코어 가격 기반 손절, 코어 변동성 타게팅, 일중 목표비중 재계산·일중 드리프트 재판정, CVaR 목적함수, 고차원 공분산 기법, ML 자산배분, 뉴스·SNS 감시, 공식 API가 있는 데이터의 스크래핑, 업비트 출금 권한, 오픈뱅킹·마이데이터 자동이체 등 — 은 설계서 어디에도 등장하지 않는다. 계획의 판정이 부적절해 보이는 경우 설계를 바꾸지 않고 **각 문서의 "이견 기록"에 남겼다**(§7).

### 4.1 조건부 분기 — 양쪽 경로를 모두 설계했다

계획이 스파이크 결과에 따라 갈린다고 명시한 지점은 **한쪽만 고르지 않고 양쪽을 설계**했다. 스파이크 결과가 나오면 **설계 변경이 아니라 config 값 전환**으로 경로가 결정되도록 배치한 것이 공통 원칙이다.

| 스파이크 | 분기 내용 | 설계 처리 |
|---|---|---|
| **SP-C4** | 절세계좌(ISA/연금/IRP) API 주문 가능 여부 → A2 자동 집행 vs A4 적립식 예약 + A3 지시서 | `accounts[].mode`(`AccountMode`) 값 분기로 흡수. 상위 리밸런서는 분기를 모른다(08 §router). 스키마는 양쪽 동일 |
| **SP-C1** | 과표기준가 자동 수집 가능 여부 | `tax.basis_price_source: fallback` 기본, 성공 시 `api` 한 줄 전환(04·10) |
| **SP-C3** | 미국 LOC/MOO/LOO 주문 지원 여부 | 미지원 시 장중 지정가가 기본 경로. `OrderType` enum은 양 경로 공통, FX 스냅샷 시점만 변경(08·07) |

### 4.2 출처 태그 단일화 — 교차 정합의 대표 사례

주문의 출처를 나타내는 타입이 초안에서 세 문서에 서로 다른 이름·값 집합으로 존재했다(02 `OrderIntent` / 08 `LegKind` / 10 `OrderOrigin`). 이 상태로 구현하면 **E7 상폐 사전 이전 주문의 pre-trade 면제 판정이 문서마다 다른 키를 보게 되어** 오작동한다. 교차 정합 단계에서 다음과 같이 단일화했다.

- 값 집합·타입·영속 필드의 정본은 **02 `core.models.OrderIntent` / `Order.intent` 하나뿐**이다(02 [DD-02-17]).
- 08은 `LegKind`를 **폐지**하고 `OrderDraft.origin: OrderIntent`를 직접 쓴다. 07 `PlannedLeg.origin` → `OrderDraft.origin` → `Order.intent`는 **전 구간 항등 사상**이다.
- 10의 `OrderOrigin`·`PlannedOrder.origin`과 8값 열거는 폐지했다. 매도/매수 세분(`E7_TRANSFER_SELL` 등)은 새 enum 값이 아니라 **`intent × side` 조합**으로 표현한다.
- 03 `orders` DDL에 `intent TEXT NOT NULL`을 추가했다(값 집합은 02 참조, 재열거 금지).

같은 단계에서 **SAFE_MODE 매도 차단의 구멍**도 메웠다 — 07이 `TARGET_SHIFT`를 밴드 복귀로 접어버려 "목표비중 하향 매도"를 판별할 기호가 소멸했고, 그 결과 08 `safemode_filter`가 계획의 금지 4종 중 ①을 원리적으로 판별하지 못했다. 세 곳을 모두 고쳐 해소했다 — 07이 `TARGET_SHIFT`를 [DD-07-19]로 독립 보존하고, 08 §4.4가 `SAFE_MODE_SELL_DROP`에 그 값을 편입했으며, 08 §4.2가 `quantize_partial(…, origins=plan_origins)`로 호출해 태그가 draft까지 도달하도록 배선했다. **셋 중 마지막 배선이 빠지면 앞의 둘이 있어도 판별되지 않으므로** 07 §21.1이 이를 계약 테스트로 고정한다.

## 6. 품질 보증 절차 — 이 세트가 거친 검사

설계서는 **작성 → 독립 검증 → 교차 정합** 3단계를 거쳤다. 각 단계는 담당자가 서로 다르며, 검증·정합 담당자는 저자와 독립적으로 계획 문서를 직접 대조했다.

| 단계 | 방법 | 결과 |
|---|---|---|
| **1. 작성** | 문서별 저자가 담당 계획 문서를 완독하고 키워드 검색으로 타 계획 문서에 흩어진 조항을 수거해 작성 | 16종 19,891줄 |
| **2. 독립 검증** | 문서별 검증자가 **역추적 대조** — 설계서가 단정한 모든 수치·enum·필드명·TR ID·법령값을 목록화하고 계획 문서에서 출처를 검색. 출처도 DD 선언도 `[확인 필요]` 표기도 없으면 환각으로 판정해 직접 수정 | **수정 352건 · 환각 처리 169건** · 조율 요청 155건 · 잔여 critical/major 33건 |
| **3. 교차 정합** | 4축(기호·enum / DB 스키마·config 키 / 모듈 인터페이스·의존 규율 / 수치 파라미터) 교차 점검 후, 발견 사항 + 조율 요청 + 잔여 이슈를 문서별로 묶어 반영. **소유 문서 우선 순서**로 처리 | 발견 **35건**(critical 7 · major 20 · minor 8) → **반영 348건** · 보류 100건 |

검증 단계에서 잡힌 환각의 실제 유형:

- **계획에 근거 없는 외부 API 단정** — 예: 업비트 인증 방식을 단정(해당 용어가 계획 문서 전체에 한 번도 등장하지 않음) → 삭제 후 `[확인 필요]`로 강등.
- **출처 오기** — `03 §2.4`로 표기된 값이 실제로는 `§2.2`에 있는 등, 한 문서에서만 6건.
- **단위 혼동** — `threshold_pct` 기본값을 `0.005`로 적었으나 계획의 YAML 리터럴은 `0.5`. 구현하면 100배 오차.
- **미선언 설계 결정** — 계획에 없는 결정이 DD 선언 없이 표에만 존재 → DD로 승격.

3단계에서 **보류 100건**은 대부분 ① 이미 반영되어 있던 항목 ② 소유권상 다른 문서가 처리해야 하는 사안 ③ 계획 개정이 선행되어야 하는 사안이다. 각 문서의 "미해결 항목" 절에 사유와 함께 남아 있다.

## 8. 문서 유지 규칙

1. **계획이 개정되면 설계가 따라간다.** 역방향은 없다. 계획 개정 시 해당 설계서의 "계획 문서 추적표"로 영향 범위를 찾는다.
2. **정의를 바꿀 때는 소유 문서만 고친다.** 사본을 먼저 고치면 두 벌이 생긴다. 소유 문서를 고친 뒤 참조 문서를 검색해 인용을 맞춘다.
3. **스파이크 결과 반영은 `[확인 필요]` 항목의 치환이다.** 해당 표기를 확정 값 + 출처(실측 일자·문서)로 교체하고, 미해결 항목 절에서 제거한다.
4. **새 결정은 DD로 선언한다.** 번호는 문서별 연속(`DD-<문서번호>-<일련번호>`), 각 문서 말미 DD 목록표에 등재한다.
5. **모든 설계서는 표준 구조를 유지한다** — 범위·정본 헤더 / 본문 / 계획 문서 추적표 / DD 목록 / 미해결 항목. 16종 전부 이 구조를 갖추고 있다.
