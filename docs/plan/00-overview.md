# 00. 프로젝트 개요 — 비전, 요구사항, 설계 원칙

> 이 문서 세트(`docs/plan/00~07`)는 oh-my-robo-advisor 구현의 **단일 정본**이다. 문서 간 수치·스펙이 충돌하면 각 영역의 정본 문서(집행 스펙 = 02, 안전장치 파라미터 = 03, 모듈 구조 = 01, 실시간·감시 = 06, 자가 개선·롤백 트리거 = 07)를 따른다.

## 1. 비전

대한민국 개인 투자자가 **본인 명의 계좌**(한국투자증권 + 업비트)를 API로 연결해, 글로벌 로보어드바이저의 검증된 자산배분 방법론과 한국 세제 최적화를 결합한 포트폴리오를 **VPS 서버에서 무인 운용**하는 자가 호스팅 시스템.

핵심 가치:

1. **검증된 것만** — 학술·실무적으로 검증된 알고리즘(Black-Litterman, Ledoit-Wolf, 밴드 리밸런싱)만 자동 집행 경로에 넣는다. 백테스트 성과가 좋아 보이는 미검증 전략은 넣지 않는다.
2. **한국 특화** — 계좌 유형별 세제(일반위탁/ISA/연금저축/IRP), 해외주식 양도세 공제, 금융소득종합과세·건강보험료 임계, KRX/미국 장 운영시간, KIS API 제약(정수 수량, 통합증거금)을 1급 시민으로 설계.
3. **잠을 잘 수 있는 무인 운용** — 확장성보다 견고함. 불확실하면 거래하지 않고 사람을 부른다(fail-safe). 모든 결정은 감사로그로 재구성 가능하다.

이 시스템에는 세 축(실시간 대응 · 시장 감시 · 자가 개선)이 있다. **셋 다 수익원이 아니다.** 실시간은 꼬리 위험 차단(보험), 감시는 집행 가능성 필터, 자가 개선은 방법론 부패 방지다. 이 성격 규정을 흐리면 세 축이 전부 과매매 장치로 변질된다 — §2.2가 그 판정 규칙이다.

### 2.1 요구 상세 [R1]~[R4]

아래 네 항목은 정식 요구사항이며, 모든 설계 문서가 `[R1]`~`[R4]` 기호로 참조한다.

| 기호 | 요구 | 연결 문서 | 충족 범위 | 미충족 / 조건부 |
|---|---|---|---|---|
| **[R1]** | 계좌·계정 연동 조작 외에는 별다른 앱 조작 없이 완전 자동 운용 | §3 등급표, 03(SAFE_MODE) | 포트폴리오 운용에 관한 강제 개입을 **연 3~6회 / 총 40~60분**으로 축소. 그중 "앱을 조작해 자산을 굴리는" 행위는 0회 | **SP-C4(절세계좌 주문 경로) 단일 변수에 의존.** 실패 시 매도형 지시서 연 1~2회 잔존. 또한 §2.2-④에 따라 **개입 0회를 목표로 삼지 않는다** |
| **[R2]** | API 한도 내 최대 활용 + 실시간 대응 강화 | 01 §5.3, 06 | 체결통보 실시간 수신, 업비트 24/7 가드 채택. 집행 창 한정 iNAV·호가 게이트는 **조건부** | **문언 그대로는 미충족.** 이 시스템은 API 한도를 최대한 소비하지 **않는다** — 소비할 이유가 없기 때문이다(`intstock-multprice` 1콜 = 30종목). 상세는 06 서두 |
| **[R3]** | 공지 파싱/스크래핑으로 거래 유의종목·거래중지 예정 종목 회피 | 06 | 충족. 단 **80%가 스크래핑이 아니라 KIS 공식 API 필드**로 해결된다(`CTPF1002R`의 `tr_stop_yn`·`admn_item_yn`·`etf_etn_ivst_heed_item_yn`·`lstg_abol_dt`, 종목마스터 `.mst.zip`) | 진짜 값어치는 위험 회피가 아니다(우리 유니버스 base rate ≈ 0). **집행 가능성 필터 = P9 오발동으로 인한 자기 유발 전면 HALT 방지**가 실질이다. KIND 스크래핑·업비트 공지 파싱은 채택하지 않는다 |
| **[R4]** | 새 개념·기존 개념 변경을 주기적으로 확인해 스스로 보완·업데이트 | 07 | 충족. 실질 산출물은 **M10a(수집기 + 다이제스트, 2주)** 뿐 | 성공 지표는 "채택한 개선의 수"가 아니라 **"놓친 부패의 수 = 0"**. 실계좌 반영은 예외 없이 사람 승인 |

각 요구의 충족 범위·미충족 부분은 해당 문서 서두에 다시 기술한다. **요구를 형식적으로 충족한 것처럼 쓰는 서술을 금지한다.**

### 2.2 요구와 수익이 충돌할 때의 판정 규칙

> "리밸런싱 빈도를 높여도 수익이 개선되지 않는다는 실증 근거가 확실하다면 억지로 양립시키지 말고 **수익 개선에 무조건 최대한 도움되는 방향으로** 계획 설계를 진행하라."

이 지시에 따라 **요구 충족보다 수익이 우선한다.** 근거가 없는 기능은 만들지 않고, 만들지 않았다는 사실을 문서에 정직하게 쓴다. 이 규칙이 만든 네 개의 확정 판정은 전 문서의 공통 전제다.

| # | 판정 | 근거 |
|---|---|---|
| ① | **일중 리밸런싱 판정은 영구 금지** | Daryanani(2008)의 최적 관찰 주기가 5~10거래일인데 현 설계(일 1회 판정)는 **최적 구간 밖(더 조밀)이라 늘릴 여지가 없다.** 일중 판정 추가는 순감점이다. (같은 논문이 경고한 "daily look의 소액 거래 남발"은 우리에게도 해당하며, 밴드 25%·쿨다운 5거래일·`T_min`이 상쇄한다고 보는 것은 **추론**이다 — EX-1이 사후 검증한다.) 이 논문의 논지는 *"rebalance less frequently, but look more frequently"*이며, 상대 20% 밴드 + 5~10거래일 관찰이 연 1회 리밸런싱 대비 **+30bp**다. 빈도를 더 올리라는 주장이 아니다 |
| ② | **실시간은 수익 추구 도구가 아니라 보험이다** | 평균 개선은 연 1~5bp로 무시 가능하다. 정당화하는 것은 꼬리다 — 2020-03 채권 ETF NAV 할인 8% 등 국면당 수백 bp. 그러므로 실시간의 도입 게이트도 "체결가가 좋아지는가"가 아니라 "게이트 판정이 실제로 달라지는가"여야 한다(06 §M9 진입 게이트) |
| ③ | **급락장에서 옳은 행동은 "그날 거래하지 않는 것"이지 "청산"이 아니다** | 2020-03과 2024-08-05 모두 그러했다. 서킷브레이커의 가치는 포지션 축소가 아니라 **나쁜 가격에 거래하는 것을 막는 데** 있다. 따라서 코어 가격 기반 자동 손절 금지(Kaminski-Lo: 랜덤워크 하 손절은 기대수익을 항상 감소), 코어 vol targeting 금지(Cederburg et al. JFE 2020: out-of-sample 열위). 위성 모멘텀 슬리브의 DD 축소만 유지 — 단 그 근거는 "조건 충족"이 아니라 **슬리브 상한 10%의 손실 봉인 + −5%p/년 비활성화 권고**다(05 §6.2. "전략이 자기상관을 가정하므로 조건을 충족한다"는 논리 비약이며 GEM의 2012년 이후 언더퍼폼이 반대 증거다) |
| ④ | **강제 개입 최소화 ≠ 개입 0회. 고가치 개입은 남기는 것이 옳다** | 연금저축 600만원 세액공제 미소진 1회 = **79~99만원**(13.2~16.5%)의 확정 손실이며, 이는 이 시스템 전체가 추구하는 알파 추정(연 5~21bp)을 두 자릿수 배 압도한다. "개입 0회"를 최적화 목표로 삼는 순간 세제 최적화가 열화된다. 그래서 §3에 **`waterfall_gap_check`(11/1)를 새 강제 개입으로 의도적으로 추가**했다 |

가장 과소평가된 위험은 시스템 오류가 아니라 **사용자의 과매매**다(Barber-Odean-Huang-Schwarz, JF 2022: 실시간 UI가 인과적으로 거래를 늘린다). 실시간 데이터의 UI 격리는 선택이 아니라 필수 요건이다(06).

## 3. 자동화 등급표 (정본)

"완전 자동화"라는 말은 설계 판단을 왜곡한다. 이 시스템의 정직한 정의는 **"포트폴리오 운용에 관한 앱 조작 0회 + 계정 연동·납세·선호 표명은 사람"**이다.

### 3.1 자동화 수준 정의

Full/Approve/Manual 3등급으로는 "자동이지만 거부 가능"과 "무조건 자동"이 구분되지 않고, "사전 설정"과 "매번 사람이 조작"도 뭉뚱그려진다. 무인 운용에서 이 구분이 곧 **부재 중 동작**을 결정하므로 7수준으로 나눈다.

| 코드 | 이름 | 정의 | 타임아웃 기본 동작 | 사람 개입 |
|---|---|---|---|---|
| **A0** | Full | 무조건 자동, 사후 통보만 | — | 0 |
| **A1** | Auto + Veto | 자동 실행 + **72시간 사후 거부권**(`/revert <change_id>`) | 실행 유지 | 0 (거부권은 권리이지 의무 아님) |
| **A2** | Auto-on-timeout | 브리핑 후 grace 경과 시 자동(negative-option) | **집행** | 0 |
| **A3** | Approve | 사전 명시 승인 필수 | **무행동**(직전 상태 유지) | 발생 시 1회 |
| **A4** | Setup-once | 최초 1회 설정 후 상시 자동 | — | 최초 1회 |
| **A5** | Manual | 매 발생 시 사람 조작 필수 | 미이행 상태 유지 | 발생 시 1회 |
| **HR** | Hard rail | 시스템이 자동 변경 **불가**. 사람의 선호 영역 | — | 본인 의사에 따름 |

> **A1과 A2의 차이가 설계의 핵심이다.** A2(집행)는 "오늘 무엇을 살 것인가" — 되돌릴 수 있고 밴드가 흡수한다. A1(정책 변경)은 "앞으로 무엇을 목표로 할 것인가" — 되돌릴 수 있지만 되돌릴 **시간**이 필요하다. 그래서 A1에만 72시간 거부권과 카나리가 붙는다.
>
> **경계 원칙: 포트폴리오의 형태(shape)는 자동, 리스크의 크기(size)는 사람.**

**§3.2의 "잔여 개입" 열과 이 표의 관계**: §3.2에는 `0~N`으로 표기된 행이 위 4개 말고도 여덟 개 더 있다 — **P2**(목표비중 8~20%p 승인) · **P5**(신규 자산군) · **P7**(hard rail 변경) · **S1**(등급 A HALT 해제) · **S5**(`ESC_*` 승인) · **T2**(외부 금융소득 확인) · **T8**(인출 플랜) · **I3**(자가 개선 승격). 이들이 소계에서 빠진 이유는 **"정상 연도"의 정의 때문**이다:

- **P2·P3·P5·S5·I3**는 **사건이 발생해야** 생기는 개입이고, 그 사건의 기대 빈도가 연 0회다(P2는 월 1회 배치에서 8%p 이동이 나와야 하고, S5는 우리 유니버스 base rate ≈ 0인 상폐·유의종목 이벤트가 있어야 한다).
- **S1**은 P8 자가치유가 실패해야 발생하며(연 0~2회), 자가치유가 대부분을 흡수한다는 것이 03 §1.3의 설계 주장이다 — **이 항목이 실제로 연 1~2회 발생하면 소계는 연 4~8회가 된다.**
- **P7**은 본인 의사 영역이라 "강제" 개입이 아니다.
- **T2**는 임계 70% 도달 시에만, **T8**은 인출기에만 발생한다.

**즉 소계는 "0회로 기대되는 조건부 항목을 제외한 값"이며, 사건이 나면 그만큼 늘어난다.** 이 표를 상한으로 읽으면 안 된다.

O2를 "개발 행위"로 분류해 합계에서 빼지 않는다 — **의존성 보안 업데이트는 운용의 일부**다.

> **정직성 표기**: 이 표는 **SP-C4(절세계좌 API 주문)가 성공한 경우**의 값이다. 실패하면 E2에서 연 1~2회 지시서 이행이 추가되고, 그것은 명백히 "앱 조작"이므로 [R1]은 "거의 달성"이 된다. SP-C4는 M1 최우선 배치 스파이크다.

## 5. 설계 원칙 (전 문서 공통)

1. **단일 프로세스, 단일 진실원** — 봇 엔진·스케줄러·웹·Telegram을 하나의 asyncio 프로세스에. 쿠버네티스/마이크로서비스/메시지큐/Redis 의도적 배제.
2. **dry-run 분기는 브로커 어댑터 최하단에만** — 상위 레이어는 자신이 모의인지 모른다. `AccountMode`(AUTO / BROKER_SCHEDULED / INSTRUCTION) 분기도 같은 패턴으로 `execution/router.py` 한 곳에 격리한다.
3. **결정은 코드, 서술은 LLM** — LLM은 주문 경로에서 import조차 불가(import-linter로 CI 강제).
4. **모든 결정은 append-only 감사로그** — "왜 그 주문이 나갔는가"를 1년 뒤에도 재구성. **미집행 주문("이 판정이 없었다면 무엇이 일어났을 것인가")도 기록 대상이다** — tracking error 분해의 입력이므로 선택이 아니라 필수 요건.
5. **실패는 안전한 쪽으로** — 판정 불가 → 거래 안 함. 자동 전량 청산은 절대 없음. (원칙 10이 이것을 정밀화한다.)
6. **파라미터는 코드가 아닌 설정** — 세법·밴드·임계값은 versioned YAML(effective-date), 하드코딩 금지.
7. **게이트는 시간+무사고 기반** — "코드 완성"이 아니라 "N주 무사고 운용"이 다음 단계 진입 조건.
8. **감시는 조밀하게, 목표 변경은 드물게** — 네 축을 분리한다. ①목표비중(월 1회) ②드리프트 밴드 판정(일 1회) ③가용성·리스크 이벤트(일 1회 배치, 집행 중 실시간) ④집행 품질(실시간, 집행 창 내). Vanguard 실증이 반대하는 것은 ①②의 빈도이지 ③④가 아니다.
9. **관측 계층은 결정을 만들 수 없다(단조 축소·일방향 밸브)** — `research`(LLM)·`realtime`(집행 가드)·`surveillance`(시장 감시)·`labs`(자가 개선)는 확정된 계획을 **줄이거나 멈추거나 제안**할 수만 있고, 수량·방향·목표비중을 **생성**할 수 없다. import-linter로 CI 강제. 원칙 3의 일반화다.
10. **정지는 안전의 동의어가 아니다** — 무인 운용에서 전면 정지는 "리밸런싱하지 않겠다"는 능동적 포지션이며 하락장에서는 그 자체가 리스크다. fail-safe의 기본 목적지는 `STOPPED`가 아니라 `SAFE_MODE`이며, 장부 무결성이 의심되는 경우(등급 A)에만 `HALTED`다. 원칙 5를 이것으로 정밀화한다.

## 6. 의도적으로 하지 않는 것

자동화 확대와 짝을 이루는 **자동화 금지 목록**이 없으면 §3의 등급표가 근거를 잃는다. 4개 군으로 그룹핑한다.

### 6.1 투자 판단

| 항목 | 이유 |
|---|---|
| LLM 기반 매매 판단 | 실증적으로 시장을 못 이김(AI-Trader). 서술 전용이며 **주문 경로 import 자체를 CI로 금지** |
| **자동 전량 청산 / 감지 후 자동 매도(`ESC_LIQUIDATE` 자동화)** | 유의종목 지정 당일 −10~43%, ETF 유의종목은 30분 단일가 전환 — 감지 후 자동 매도는 **최악의 가격에 파는 것을 자동화**하는 것. ETF는 정리매매 없이 해지상환되므로 방치해도 NAV로 현금화된다. 근거는 기술적 불가능이 아니라 **오탐 비용의 비대칭성**. **예외는 §3.2 E7(상폐 D−10 사전 이전) 하나뿐**이며, 그 예외가 정당한 이유는 목적이 위험 회피가 아니라 과세 시점 통제이고 **상한 4개(승인 페어 1:1 · 분할 · 2소스 교차 확인 · 과세 이득 계좌 한정)**로 봉인되기 때문이다. **위성 슬리브 DD −25% 코어 회수(02 §6)는 "청산"이 아니라 코어로의 이전이며, SAFE_MODE·P1 발동 중에는 `safemode_filter`가 제거한다** |
| **코어 자산의 가격 기반 자동 손절** | Kaminski-Lo: 랜덤워크 하에서 단순 손절은 기대수익을 **항상** 감소시킨다. 위성 슬리브의 DD 축소를 유지하는 근거는 "모멘텀이므로 조건 충족"이 아니라 **손실 상한이 10%로 봉인되어 있다는 구조적 사실**이다(05 §6.2 정정) |
| **코어 변동성 타게팅 / 실시간 리스크 레벨 조정** | Cederburg et al.(JFE 2020) — 실시간 구현 가능한 버전은 unmanaged 대비 낮은 Sharpe. 크립토 슬리브의 주 1회 갱신만 조건부 유지(근거 "중간") |
| **실시간 신호에 의한 목표비중·수량·방향 생성** | 원칙 9(일방향 밸브). 실시간 채널은 주문을 **줄이거나 멈출 수만** 있고 새로 만들거나 키울 수 없다. `realtime -/-> engine.optimizer` import-linter 강제 |
| 퀀트 팩터 개별주 위성 | point-in-time 재무데이터 파이프라인이 코어 전체와 맞먹는 비용. 편익이 그 비용을 넘는다는 근거가 없다 |
| **ML 자산배분 · LLM 알파 마이닝** | "ML은 실패한다"는 반증 가능한 과장이므로 쓰지 않는다. 정확한 근거는 **"우리 문제는 N≈10, 월 1회 재추정, 짧은 표본 — ML이 이기는 조건(고차원·대량 표본·저비용 집행)을 하나도 갖추지 못했다"** |
| **고차원 공분산 기법**(nonlinear shrinkage/QIS, denoising, **detoning**, NCO, HERC) | 집중비율 `c = N/n ≈ 0.011~0.016`(N≈8~12, n=756). 이들은 전부 `c → 1` 문제의 처방이다. 특히 **detoning(시장 요인 제거)은 자산배분에서 유해** — 시장 요인은 우리가 배분하려는 대상 그 자체다 |
| **CVaR / EVaR / CDaR 목적함수** | 756 관측치 × 5% = **38개 관측치**가 CVaR 전체를 결정. 02 §3.1-5 "표본평균 기대수익은 코드 경로 자체가 없다"의 정면 위반. 리포팅 지표로만 산출 |
| 뉴스·SNS·커뮤니티 감시 | 신호대잡음 최악이며 prompt injection 표면. "LLM 기반 매매 판단" 금지의 연장 |

### 6.2 자동화 범위

| 항목 | 이유 |
|---|---|
| **일중 목표비중 재계산 · 일중 드리프트 밴드 재판정** | **영구 금지.** §2.2-①. 룩백 756영업일 입력에 초 단위 갱신은 정보이론적 순손실이며, Daryanani도 daily look은 "profusion of small trades"로 역효과라고 명시했다 |
| **상시 실시간 스트리밍 · 다종목 상시 감시** | WS 41건 예산을 상시 감시에 쓰면 정작 집행 중 호가를 못 받는다. 실시간은 **집행 창 한정**이며, 창 밖에서는 T0 채널(업비트 ticker)과 REST 스냅샷만 사용한다 |
| 자동 코드 배포(CD) / **LLM의 직접 코드 수정** | 돈을 다루는 프로세스는 수동 승인 배포. 신규 근거: 자가 개선 에이전트가 자기 평가함수(게이트·스냅샷·실험 로그)에 접근하면 "통과"가 무의미해진다 — 이는 악의가 아니라 **정직한 최적화의 결과**로 발생한다 |
| **`risk.level`·목표금액·자금 상한·kill switch 임계의 자동 변경** | hard rail 명문화. 형태(shape)는 자동, 크기(size)는 사람 |
| **DAXA 타 거래소 공지 교차 감시** | BTC/ETH 고정 유니버스에서 발생확률 ≈ 0. 유지보수 부채만 발생 |
| **미국 LULD pause 실시간 추적** | **조건부 제외** — 미국 기본 경로가 LOC(종가 체결)인 경우에 한해 장중 halt 노출이 구조적으로 작다. **SP-C3에서 LOC/MOO/LOO 미지원이 확인되어 장중 지정가가 기본 경로가 되면 이 판정은 무효**가 되며, 06 §5.1 감시 카탈로그의 재검토 항목으로 승격한다(06 부록 A US-03 동일) |
| **KIND 스크래핑 · 업비트 공지 파싱** | base rate ≈ 0인 이벤트에 대한 스크래핑 소스는 유지보수 부채다. 필요한 정보의 80%는 KIS 공식 API 필드에 이미 있다 |

### 6.3 기술 스택

| 항목 | 이유 |
|---|---|
| 소수점 매매·환전 API 의존 | KIS 미제공 — 정수 수량 최적화 + 통합증거금(원화 주문→자동환전) 전제 |
| 미국 주간거래(Blue Ocean) 집행 | 유동성 얇음·세션 취소 전례 — 코드 레벨 금지 |
| NXT/SOR 주문 | KRX 정규장 단순 주문만. 검증 표면 축소 우선 |
| Kubernetes/Celery/PostgreSQL/React SPA | 단일 사용자 부하에 과잉. SQLite+Parquet, htmx로 충분 |
| **공식 API가 존재하는 데이터의 스크래핑** | 하드 규칙. KIS 종목마스터·`CTPF1002R`·업비트 `market_warning`으로 대체 가능한 것은 전부 대체한다. 전종목 벌크 스크래핑 금지 — 필요하면 공식 배포 마스터파일을 쓴다 |
| **in-process 이벤트 버스(pub/sub) · 구독 축약 사다리** | 구독자가 토픽당 1~2개뿐인 시스템에 간접층만 만든다. decoder가 가드 함수를 직접 호출하고 체결(Fill)만 `asyncio.Queue`로 분리한다. 구독 관리는 `used + requested > 38`일 때 **등록 거부 + 해당 종목 REST 폴백 + warning**(어서션이 아니라 명시적 분기 — 정본은 06 §1.3) + 종목 상한 9개 하드캡으로 충분 |

### 6.4 법·보안

| 항목 | 이유 |
|---|---|
| 해외 브로커(IBKR 등) 직접 연동 | 국내 거주자의 해외상장 증권 매매는 국내 증권사 경유 의무(외국환거래규정) |
| **감시 파이프라인 내 LLM 파싱** | **필수 하드 규칙.** 공지 본문 파싱을 LLM에 맡기면 **prompt injection이 집행 경로에 직결**된다. 감시 파서는 전부 결정론적 구조 파서(정규식 + Pydantic 스키마 검증)다. 자연어 요약이 필요하면 그것은 `research/` 레이어의 일이며 산출물은 사람이 읽는 리포트로만 흐른다. `surveillance -/-> research` import 금지 |
| **오픈뱅킹 / 마이데이터 기반 자동 이체** | 오픈뱅킹 실서비스는 최소 개인사업자 등록 + 이용기관 등록·보안점검(기본 1천만원대). 마이데이터는 금융위 **허가업**. 전송요구권은 개인에게 API 엔드포인트를 주는 제도가 아니다 |
| **금융기관·국세청 로그인 자격증명의 제3자 위탁**(스크래핑 대행 상용 API) | 01 §7 시크릿 최소화·Tailscale 폐쇄망 원칙과 정면 충돌 |
| **업비트 출금 권한 활성화** | 출금 권한을 켜면 **키 유출 = 자산 유출**. 자동화 편익 < 키 유출 시 손실 상한 |
| **복수 앱키·타인 계좌를 통한 API 한도 우회** | §7 법적 전제 위반. 커뮤니티에 통용되는 패턴이나 본 시스템은 채택하지 않는다 |

## 7. 법적 전제

- 본인 명의 계좌·본인 자금의 API 자동매매는 등록 대상 아님(자본시장법상 투자일임업은 "타인을 위한 영업행위"에 적용).
- 허수성 호가 등 불공정거래 규정은 개인 알고리즘에도 적용 — 단순 지정가/시장가 주문만 사용, 정정·취소 빈도 상한(서킷브레이커 P4)과 회전율 일일 예산(P11)으로 방어.
- 타인 계좌 API 키 수탁·운용·대가 수취는 무등록 투자일임업(형사처벌). 상용화하려면 투자일임업 등록(자기자본 15억) + 코스콤 RA 테스트베드(약 7개월) — [04-roadmap.md](04-roadmap.md) 부록 참조. 현재의 BYO-key 자가 호스팅 구조를 유지하는 한 이 문제는 발생하지 않는다.
- **미국 PTP(Publicly Traded Partnership) 종목**은 IRS §1446(f)에 따라 **매도 대금 총액(gain이 아님)에 10% 원천징수**된다. 코어 후보에는 해당 종목이 없으나 위성·대체 페어 교체 시 사고가 가능하므로, 02 §2.3 유니버스 필터에 `ptp_item_yn == 'N'`을 **hard 조건**으로 둔다(KIS 해외 `search_info`가 필드를 제공).
